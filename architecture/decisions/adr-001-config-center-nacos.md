# ADR-001: 配置中心选用 Nacos（而非 Consul / Apollo）

| 项目 | 内容 |
|------|------|
| **状态** | accepted |
| **日期** | 2026-11-13 |
| **决策者** | 后端负责人（架构）、运维负责人 |
| **影响范围** | 全部 12 个 Spring Boot 服务、3 套环境、发布流程 |
| **关联** | [[architecture/service-governance-config-center|服务治理与配置中心技术对比]] |

## 背景与约束

### 现状

- 12 个 Spring Boot 服务的配置分散在 `application-{env}.yml` 与 K8s ConfigMap 中，共 3 套环境。
- 修改任一运行时参数（连接池大小、限流阈值、开关）需重建镜像或滚动重启，全量重启约 **20 分钟**。
- 三个月内发生过 **1 次**测试环境配置误合并到生产分支，导致核心接口 500 持续 **40 分钟**。
- 变更无审计记录，出问题后无法回答"谁在什么时候改了什么"。

### 硬约束

- 团队 6 人，**无专职运维**，不引入需要独立维护的新组件栈。
- 技术栈已基于 Spring Cloud Alibaba，客户端改造量越小越好。
- 配置变更需**可审计、可回滚**（合规要求保留 6 个月变更历史）。
- 部署环境为 K8s，需支持按命名空间隔离多环境。

### 不变量

- 本次不改变服务注册发现方案（原为 Eureka，后续单独决策）。
- 不引入配置加密方案（密钥继续走 K8s Secret）。

## 决策

我们决定 **采用 Nacos 1.x 作为统一配置中心 + 服务注册中心**，
配置持久化到 MySQL（CP 语义），服务发现使用 AP 模式。

关键理由：

1. **Spring Cloud Alibaba 原生支持**，客户端只需引入 `nacos-config` 依赖 + 一个 `bootstrap.yml`，
   12 个服务的改造成本约 2 人天；Apollo 需要额外部署 Config Service / Admin Service / Portal 三套组件。
2. **同一套组件同时解决服务注册与配置管理**，对没有专职运维的 6 人团队，少维护一个 Consul 集群是实质性收益。
3. **命名空间天然映射环境**，配合 MySQL 存储可满足变更历史与回滚的合规要求。

## 候选方案与否决理由

| 方案 | 核心思路 | 优势 | 致命缺陷 / 否决理由 |
|------|----------|------|----------------------|
| **Nacos（采纳）** | 注册中心 + 配置中心一体，AP/CP 可切换 | 组件少、接入快、控制台够用 | 控制台权限模型较粗，灰度推送能力弱于 Apollo；需自行承担 MySQL 高可用 |
| Consul | HashiCorp 生态，Raft 强一致，原生多数据中心 | 多数据中心能力强、KV 通用 | **无配置版本管理与发布审批**，回滚要自己写脚本；团队无人熟悉 Raft 运维 |
| Apollo | 携程开源，配置管理能力最完整（审批、灰度、权限） | 灰度发布与权限模型最成熟 | 需部署 3 个组件 + Eureka + MySQL，**运维成本超出 6 人团队承受范围**；与服务注册仍是两套系统 |
| K8s ConfigMap + Reloader | 复用现有 K8s 能力，零新增组件 | 零成本、声明式 | **不支持运行时热更新**（Reloader 触发的仍是滚动重启），且无审计与回滚；本次痛点未被解决 |

> 否决理由均基于**当前约束**。若后续团队扩至 20 人以上且出现按流量比例灰度配置的强需求，
> Apollo 应被重新评估（见文末复审触发条件）。

## 后果

### 正面

- 参数类变更从"20 分钟重启"降为"秒级推送生效"，大促期间可实时调整限流阈值。
- 配置变更全部落库，可查询操作人、时间、前后值，满足审计要求。
- 环境隔离由命名空间保证，误合并风险显著下降。

### 负面

- 新增一个有状态依赖：**Nacos + MySQL 集群成为所有服务的启动前置条件**，
  一旦不可用，服务冷启动会失败（缓解：客户端本地快照 + 启动容错）。
- 配置中心权限模型较粗，无法限制"某团队只能发布某命名空间"，需靠流程约束。
- 团队需额外学习 Nacos 的集群部署与运维（约 1 人周）。

### 风险与缓解

| 风险 | 触发条件 | 影响 | 缓解措施 | 责任人 |
|------|----------|------|----------|--------|
| 配置中心故障导致全站冷启动失败 | Nacos 集群或 MySQL 不可用 | 服务无法启动（P0） | 开启客户端本地快照 `nacos.config.cache`，启动时降级读本地文件；Nacos 3 节点 + MySQL 主从 | 运维负责人 |
| 错误配置瞬间扩散到全部实例 | 误操作发布 | 全站异常 | 关键配置分命名空间隔离；引入"发布前 diff 确认"；保留 30 秒内的快速回滚 | 后端负责人 |
| 配置项散落无归属 | 长期演进 | 无人敢删的死配置 | 配置项必须带 owner 注释，季度清理 | 后端负责人 |

## 验证方式

- **观测指标**：
  - 配置变更到全部实例生效时间 P95 < 3 秒
  - 因配置问题导致的故障次数：基线 1 次/季度 → 目标 0 次/半年
  - 服务冷启动对配置中心的强依赖失败率 < 0.1%
- **复盘时间**：迁移完成后 1 个月

## 复审触发条件

- 出现按**流量比例**灰度配置的强需求，且当前方案需人工分批操作超过 5 分钟。
- 服务数量或团队规模翻倍，Nacos 控制台的权限粒度成为管理瓶颈。
- Nacos 1.x 停止维护，或升级 2.x 需要引入 gRPC 长连接带来新的网络要求。
