# 高可用与稳定性设计

## 概述

高可用不是"不出故障"——**所有分布式系统都会出故障，区别只是故障发生时系统退化成什么样**。
设计目标应该这样表述：*当 A 组件不可用时，B 功能降级但仍可用，核心链路不受影响*。

这条表述里藏着两个关键认知：

1. **可用性必须量化**。"高可用"无法验收，"年停机 ≤ 52 分钟"可以验收。
2. **稳定性靠的是"有边界的失败"**。故障不可怕，可怕的是故障顺着调用链横向扩散——
   一个慢查询拖垮线程池，一个下游超时引发全站雪崩，这才是 P0 的真正成因。

> **架构师判断**：评估一个系统的稳定性，不要看它用了多少中间件，看两件事——
> **超时和重试是否逐层显式配置过**，以及**有没有一个开关能在 30 秒内摘掉故障功能**。
> 大部分雪崩都源于这两件事没做。

## 一、先用数字说话

### 几个 9 意味着什么

| 可用性 | 年停机 | 月停机 | 日停机 | 实现代价 |
|--------|--------|--------|--------|----------|
| 99% | 3.65 天 | 7.2 小时 | 14.4 分钟 | 单机 + 备份 |
| 99.9%（3 个 9） | 8.76 小时 | 43.2 分钟 | 1.44 分钟 | 主备 + 监控告警 |
| 99.95% | 4.38 小时 | 21.6 分钟 | 43.2 秒 | 双活 + 自动故障转移 |
| 99.99%（4 个 9） | 52.6 分钟 | 4.32 分钟 | 8.64 秒 | 多活 + 全链路自动化 |
| 99.999%（5 个 9） | 5.26 分钟 | 26 秒 | 0.86 秒 | 异地多活 + 无人工干预 |

**每增加一个 9，成本大致翻倍到三倍**。所以第一步不是追 4 个 9，而是问：
**这个业务挂 1 小时，损失多少钱？** 依据这个反推目标，而不是照抄大厂指标。

### 可用性公式：MTTR 比 MTBF 更值得投入

```text
可用性 = MTBF / (MTBF + MTTR)

MTBF：平均无故障时间（多久坏一次）
MTTR：平均恢复时间（坏了多久能好）
```

提升 MTBF 靠"不出事"——加冗余、加测试、加评审，成本高且收益递减。
降低 MTTR 靠"出事能快好"——监控、告警、一键回滚、降级开关、Runbook，成本低、收益线性。

> **架构师判断**：团队工程能力不足时，优先投 MTTR。
> 把 MTTR 从 60 分钟压到 10 分钟，可用性从 99.9% 提升到 99.99% 的量级；
> 而同样的钱投在 MTBF 上，通常只能减少几次小故障。

### 串联可用性：链路越长越脆弱

```text
网关(99.99%) × 服务A(99.9%) × 服务B(99.9%) × 数据库(99.95%) ≈ 99.74%
```

四个都"高可用"的组件串起来，整体只有 99.74%（年停机 22.8 小时）。
**结论有两条**：减少同步调用链长度；对非核心依赖做**降级容错**，让它挂掉不放大到主链路。

## 二、故障模型：系统是怎么坏的

设计容错前必须知道对手是谁。生产故障的绝大部分落在下面几类：

| 故障模式 | 触发条件 | 典型征兆 | 核心对策 |
|----------|----------|----------|----------|
| **单点故障** | 某组件只有 1 实例 | 该组件宕机即全站不可用 | 冗余部署 + 健康检查 + 自动摘除 |
| **级联失败（雪崩）** | 下游变慢，上游线程/连接被占满 | 上游 CPU 不高但请求全超时 | 超时 + 熔断 + 隔离 + 有界队列 |
| **重试风暴** | 大量客户端同时重试失败请求 | 下游 QPS 不降反升，越重试越死 | 指数退避 + 抖动 + 重试预算 |
| **惊群效应** | 缓存同时失效 / 定时任务同一时刻触发 | 瞬时 QPS 尖峰打到数据库 | 过期时间加随机、任务打散 |
| **慢查询拖垮连接池** | 报表类 SQL 与在线交易共用连接池 | 连接池耗尽，所有接口超时 | 读写分离、独立连接池、查询超时 |
| **队列积压** | 消费速度 < 生产速度 | 消息延迟持续增长，内存上涨 | 监控 lag、限流生产端、可丢弃分级 |
| **依赖放大** | 一个请求扇出 N 个下游 | 下游抖动被放大 N 倍 | 并行化 + 结果缓存 + 部分失败容忍 |
| **配置错误** | 阈值、连接串、开关改错 | 发布后立即异常，回滚即恢复 | 灰度发布 + 配置 diff + 快速回滚 |

**注意"重试风暴"和"惊群"**——这两种故障的特点是**系统自己把自己打死**，
靠加机器解决不了，反而会加剧。它们只能靠客户端策略和流量整形。

## 三、稳定性四件套

限流、熔断、降级、隔离是四个不同层面的保护，缺一不可，且**不能互相替代**：

| 手段 | 保护对象 | 触发方式 | 解决的问题 |
|------|----------|----------|------------|
| **限流** | 保护**自己** | 主动，按 QPS/并发数 | 超出处理能力的流量直接拒绝，避免打满 |
| **熔断** | 保护**调用方**（不被下游拖死） | 被动，按错误率/慢调用比例 | 下游故障时快速失败，释放上游资源 |
| **降级** | 保护**核心链路** | 主动，人工或规则触发 | 摘掉非核心功能，把资源让给核心 |
| **隔离** | 限制**故障影响范围** | 静态，按资源池划分 | 一个依赖的故障不扩散到其他依赖 |

### 3.1 限流：选对算法

| 算法 | 原理 | 允许突发 | 平滑度 | 适用场景 |
|------|------|----------|--------|----------|
| **固定窗口计数** | 每窗口计数，超限拒绝 | 有，且窗口切换处可放过 2 倍 | 差 | 粗粒度保护，实现最简单 |
| **滑动窗口** | 按时间片段统计，窗口滑动 | 有小幅突发 | 较好 | 通用限流（Sentinel 默认） |
| **漏桶** | 请求入桶，匀速流出 | **不允许**，强制匀速 | 最好 | 保护脆弱下游（老系统、第三方 API） |
| **令牌桶** | 按速率发令牌，桶容量即突发上限 | 允许，上限为桶容量 | 好 | 通用场景（Guava RateLimiter） |

参数怎么定，比选算法更重要：

```text
阈值上限 = 单机压测容量 × 0.7        # 留 30% 应对流量毛刺
集群阈值 = 单机阈值 × 实例数 × 0.8    # 扣除实例不均与扩容延迟
```

**限流阈值必须能被压测证伪**。凭感觉填的阈值，要么形同虚设（填太高），要么成为故障源（填太低）。

### 3.2 熔断：参数决定它是保护还是伤害

熔断器是三态机，关键在参数：

```text
CLOSED ──(错误率超阈值且样本足够)──▶ OPEN ──(冷却时间到)──▶ HALF_OPEN
  ▲                                                            │
  └────────────────(试探成功)───────────────────────────────────┘
                              (试探失败)──▶ OPEN
```

| 参数 | 常用值 | 说明 |
|------|--------|------|
| 错误率阈值 | 50% | 太低会误熔断（正常抖动），太高失去保护意义 |
| 慢调用比例阈值 | 慢调用 RT > 1s 占比 60% | 只统计错误率会漏掉"变慢但不报错"的故障 |
| 最小请求数 | 20 | 样本太少时统计无意义，避免冷启动即熔断 |
| 冷却时间（OPEN 时长） | 5~30 秒 | 太短频繁试探加剧下游压力，太长恢复慢 |
| 半开放行量 | 1~5 个请求 | 试探要少，否则等于没熔断 |

**最常见的配置错误是只按错误率熔断**。下游"变慢但返回 200"的故障不会触发熔断，
但它对上游的伤害和报错一样——线程一样被占满。所以**慢调用比例必须一起配**。

### 3.3 降级：按功能分级，而不是按心情

降级的前提是**分级**。上线前就该确定：哪些功能可以挂，哪些绝对不能。

| 级别 | 功能 | 降级策略 | 可接受时长 |
|------|------|----------|------------|
| **P0 核心** | 下单、支付、登录 | 不降级，只做限流保底 | 不可用即 P0 事故 |
| **P1 重要** | 商品详情、订单列表 | 返回缓存/静态兜底页 | 30 分钟内可接受 |
| **P2 次要** | 推荐、评价、积分 | 直接返回空，前端隐藏模块 | 数小时可接受 |
| **P3 可关** | 埋点、报表、消息推送 | 关掉，不告警 | 一天可接受 |

降级的三种实现形态：

1. **开关降级**——配置中心的开关（最常用，必须能在 30 秒内生效）。
2. **兜底数据降级**——读缓存或静态默认值，返回"暂无数据"而不是报错。
3. **旁路降级**——跳过非核心步骤（如跳过风控的二次校验，仅记日志后补）。

> **降级开关必须有 owner 和默认值**。没人知道怎么拨的开关，等于没有开关；
> 默认值为"开"的开关，会在第一次故障时把系统锁死。

### 3.4 隔离：把爆炸半径关在笼子里

| 隔离层次 | 做法 | 隔离粒度 | 代价 |
|----------|------|----------|------|
| **线程池隔离** | 每个下游独立线程池 | 依赖级 | 线程数上升，上下文切换开销 |
| **信号量隔离** | 限制并发数而非独立线程 | 依赖级 | 无法异步，适合轻量调用 |
| **连接池隔离** | 不同业务用不同连接池 | 业务级 | 连接数消耗（数据库连接宝贵） |
| **集群/分组隔离** | 核心业务独立部署 | 业务级 | 机器成本翻倍 |
| **机房/单元隔离** | 单元化，故障限制在单元内 | 地域级 | 架构复杂度最高 |

最小可落地的一步：**把报表/导出类查询与在线交易的数据库连接池分开**。
这一条能消灭生产上相当比例的"慢查询拖垮全站"故障。

## 四、被低估的两件事：超时与重试

### 4.1 超时链：必须逐层收敛

```text
用户 → 网关(3s) → 服务A(2s) → 服务B(1.5s) → 数据库(1s)
```

**下游超时必须小于上游**，逐层收敛。反例是全部用默认值（很多框架默认无限等待或无超时），
结果是数据库卡住 30 秒，上游早就在 3 秒时放弃了，但连接和线程还占着——
**请求已经失败，资源却还在被消耗**，这才是雪崩的真正机制。

三条硬规则：

1. 每一层都必须**显式**设置超时，禁止依赖框架默认值。
2. 下游超时 < 上游超时 × 0.8（留出重试与序列化时间）。
3. 数据库、HTTP 客户端、消息消费都必须有超时，包括**连接超时**和**读超时**分别设置。

### 4.2 重试预算：不加预算的重试是自伤

重试能救"偶发失败"，但会放大"持续故障"。三条约束：

- **只重试可重试的错误**：网络超时、5xx、限流拒绝可以；4xx、参数错误、业务校验失败不能。
- **退避加抖动**：固定间隔重试会让所有客户端同时发力，把刚恢复的下游再打挂。
- **重试预算**：单请求最多 2~3 次；服务级重试流量不超过总流量的 10%，
  超出即熔断重试（Netflix 的 Retry Budget 思路）。

## 五、代码：三个原语的完整实现

下面这段只用标准库，可直接运行，用来理解参数与状态的联动关系。

```python
#!/usr/bin/env python3
"""限流 / 熔断 / 退避三个稳定性原语的最小可运行实现（仅用标准库）。"""

import random
import time


class TokenBucket:
    """令牌桶限流：允许突发到容量上限，长期速率受 rate 约束。

    对比：漏桶强制匀速输出（无突发），固定窗口在窗口切换处会放过 2 倍流量。
    """

    def __init__(self, capacity: int, rate: float) -> None:
        self.capacity = capacity      # 桶容量 = 允许的最大突发量
        self.rate = rate              # 每秒补充的令牌数
        self.tokens = float(capacity)
        self.updated = time.monotonic()

    def allow(self) -> bool:
        now = time.monotonic()
        # 惰性补充：不用定时器，避免线程与精度开销
        self.tokens = min(self.capacity, self.tokens + (now - self.updated) * self.rate)
        self.updated = now
        if self.tokens >= 1:
            self.tokens -= 1
            return True
        return False


class CircuitBreaker:
    """熔断器三态：CLOSED 正常放行 → OPEN 快速失败 → HALF_OPEN 试探恢复。"""

    def __init__(self, fail_threshold: int = 3, open_seconds: float = 0.2) -> None:
        self.fail_threshold = fail_threshold
        self.open_seconds = open_seconds        # 真实场景通常 5~30 秒
        self.failures = 0
        self.state = "CLOSED"
        self.opened_at = 0.0

    def call(self, fn):
        if self.state == "OPEN":
            if time.monotonic() - self.opened_at < self.open_seconds:
                raise RuntimeError("熔断中，快速失败（不占用下游资源）")
            self.state = "HALF_OPEN"            # 冷却结束，放一个请求去试探

        try:
            result = fn()
        except Exception:
            self.failures += 1
            if self.state == "HALF_OPEN" or self.failures >= self.fail_threshold:
                self.state = "OPEN"
                self.opened_at = time.monotonic()
            raise
        else:
            self.failures = 0
            self.state = "CLOSED"               # 试探成功，完全恢复
            return result


def backoff_delay(attempt: int, base: float = 0.05, cap: float = 1.0,
                  jitter: bool = True) -> float:
    """指数退避 + 抖动：避免下游恢复瞬间被同时重试的请求打成雪崩。"""
    raw = min(cap, base * (2 ** attempt))
    return random.uniform(raw / 2, raw) if jitter else raw


if __name__ == "__main__":
    bucket = TokenBucket(capacity=5, rate=50)
    passed = [bucket.allow() for _ in range(12)]
    print(f"突发 12 次请求: 通过 {sum(passed)}，拒绝 {len(passed) - sum(passed)}")
    time.sleep(0.1)
    print(f"等待 100ms 后补充令牌: 通过 {sum(bucket.allow() for _ in range(12))}")

    breaker = CircuitBreaker(fail_threshold=3, open_seconds=0.2)
    calls = {"n": 0}

    def flaky():
        calls["n"] += 1
        if calls["n"] <= 3:
            raise TimeoutError("下游超时")
        return "ok"

    for i in range(6):
        try:
            breaker.call(flaky)
            print(f"第 {i + 1} 次调用: 成功，状态={breaker.state}")
        except Exception as exc:
            print(f"第 {i + 1} 次调用: {exc}，状态={breaker.state}")
        time.sleep(0.05)

    time.sleep(0.25)  # 超过冷却时间，进入半开试探
    try:
        breaker.call(flaky)
        print(f"冷却后试探: 成功，状态={breaker.state}")
    except Exception as exc:
        print(f"冷却后试探: {exc}，状态={breaker.state}")

    print("退避序列:", [round(backoff_delay(i), 3) for i in range(5)])
```

实际运行输出（退避序列带抖动，每次数值不同）：

```text
突发 12 次请求: 通过 5，拒绝 7
等待 100ms 后补充令牌: 通过 5
第 1 次调用: 下游超时，状态=CLOSED
第 2 次调用: 下游超时，状态=CLOSED
第 3 次调用: 下游超时，状态=OPEN
第 4 次调用: 熔断中，快速失败（不占用下游资源），状态=OPEN
第 5 次调用: 熔断中，快速失败（不占用下游资源），状态=OPEN
第 6 次调用: 熔断中，快速失败（不占用下游资源），状态=OPEN
冷却后试探: 成功，状态=CLOSED
退避序列: [0.036, 0.094, 0.152, 0.282, 0.7]
```

读这段输出要注意三个细节：

- 前 12 个请求只通过 5 个 —— 桶容量决定**突发上限**，速率决定**长期均值**，两者要分开设。
- 第 3 次失败后立刻 OPEN，第 4~6 次**没有真正调用下游**（`def flaky` 的计数器没涨），
  这才是熔断的价值：**放弃调用本身就是保护下游**。
- 冷却后一次试探成功即恢复 CLOSED，说明半开策略有效；若试探失败会立刻回到 OPEN。

## 六、容量与压测

### 单机容量怎么估

```text
单机 QPS ≈ 1000ms / 平均 RT(ms) × 并发线程数
例：RT 50ms、200 个处理线程 → 约 4000 QPS（理论上限，实际按 60%~70% 折算）
```

理论值必须靠压测校准。压测要回答四个问题，缺一个都不算完成：

| 问题 | 指标 | 陷阱 |
|------|------|------|
| 单机能扛多少？ | TPS/QPS 拐点 | 只看成功率不看 RT，压力上来后 3 秒返回也算"成功" |
| 瓶颈在哪？ | CPU / 连接池 / IO / 锁等待 | 不采样直接扩容，扩完还是同样瓶颈 |
| 水位多少时开始劣化？ | RT 拐点对应负载 | 只测到极限值，没测劣化拐点 |
| 长时间稳定吗？ | 24h 内 RT 与内存漂移 | 短时压测掩盖内存泄漏与连接泄漏 |

### 全链路压测的两个必备前提

1. **流量染色**——压测流量打标，避免写入真实业务数据（下单、扣款）。
2. **影子表/影子库**——压测写操作落到影子库，与生产数据物理隔离。

没有这两条就做压测，等于在生产上做随机破坏。

## 七、多活架构：先算清代价

| 形态 | 机房故障影响 | RTO | RPO | 复杂度 | 成本 |
|------|--------------|-----|-----|--------|------|
| 单机房主备 | 需人工切换 | 30 分钟~小时级 | 可能丢数据 | 低 | 1.5 倍 |
| 同城双活 | 秒级~分钟级 | < 1 分钟 | 同步复制则 RPO=0 | 中 | 2 倍 |
| 两地三中心 | 分钟级 | 1~5 分钟 | 同城 RPO=0，异地有损 | 较高 | 3 倍 |
| 异地多活（单元化） | 单元内故障自愈 | < 30 秒 | 单元内 RPO=0 | 最高 | 3~5 倍 |

**单元化是异地多活的唯一可行解法**：按用户 ID 分片（如按 uid 取模分单元），
每个单元内闭环（含数据库），故障只影响该单元的用户。代价是**跨单元查询基本不可用**、
数据同步链路复杂、扩容需重新分片。

> **架构师判断**：业务还没到日订单百万级，不要碰单元化。
> 同城双活 + 快速故障转移能覆盖 95% 的可用性需求，剩下的部分用"故障时降级为写只读"补齐更划算。

## 八、混沌工程：把故障演练成日常

混沌工程不是"随机杀机器"，是有假设的实验：

| 步骤 | 内容 |
|------|------|
| 1. 定稳态指标 | 用可量化的业务指标（成功率、P95），不是"看起来正常" |
| 2. 提出假设 | "杀掉 1/3 订单实例，成功率不低于 99%" |
| 3. 控制爆炸半径 | 先在预发，再灰度 1% 流量，最后全量 |
| 4. 注入故障 | 延迟、异常、实例宕机、网络分区、磁盘满、依赖超时 |
| 5. 验证与修复 | 假设不成立即发现一个真实缺陷，补进 Runbook |

**最小可行的起点不是 ChaosBlade，而是每月一次的手动演练**：
在预发环境手动摘掉一个依赖，看系统是否按设计降级。这一步就能暴露大部分"降级开关从没被验证过"的问题。

## 九、故障应急与复盘

### 应急三件事

1. **止血优先于定位**。先回滚/降级/扩容，让用户可用，再查根因。**先定位后止血是新手最常犯的错**。
2. **单一指挥者**。故障期间必须有人拍板（谁回滚、谁沟通），多头指挥会延误决策。
3. **Runbook 先行**。每个 P0 服务必须有一页纸：怎么回滚、开关在哪、找谁、看哪个看板。

### 复盘要问的问题

| 问题 | 目的 |
|------|------|
| 故障直接原因是什么？ | 表层现象 |
| 为什么没有在更早的环节被拦住？（监控/告警/测试/评审） | 找到体系缺口 |
| 如果当时有一个开关，问题能多快止血？ | 评估降级能力 |
| 同类故障历史上发生过吗？ | 检验上次复盘是否落地 |
| 有哪些动作能降低 MTTR？ | 优先投 MTTR |

复盘结论必须落到**可验证的动作**（加哪条告警、哪个接口补超时、哪个开关纳入演练），
落到"加强规范意识"就等于没复盘。

## 十、度量：用 SLO 而不是"可用率"驱动

| 概念 | 定义 | 示例 |
|------|------|------|
| **SLI**（指标） | 实际测量值 | 下单接口成功率、P95 延迟 |
| **SLO**（目标） | 对 SLI 的内部目标 | 成功率 ≥ 99.9%，P95 ≤ 300ms |
| **SLA**（协议） | 对外承诺，通常低于 SLO | 月度可用性 ≥ 99.5% |
| **错误预算** | 1 - SLO 允许的失败额度 | 99.9% → 每月 43 分钟不可用额度 |

错误预算的真正用途是**决策依据**：预算充足时可以激进发版；预算耗尽时冻结变更、优先还稳定性债。
它把"要不要发版"从争论变成算术。

## 常见反模式

| 反模式 | 表现 | 后果 | 纠正 |
|--------|------|------|------|
| 只加机器不做隔离 | 一出问题就扩容 | 瓶颈在连接池/锁时无效，成本白花 | 先定位瓶颈再加容量 |
| 无限重试 | 失败就重试 3 次且无退避 | 重试风暴，把下游彻底打挂 | 退避 + 抖动 + 重试预算 |
| 熔断只配错误率 | 下游变慢不报错 | 线程被占满，与宕机等效 | 同时配慢调用比例 |
| 降级开关无验证 | 开关从没被拨过 | 真出事时拨了没效果 | 纳入混沌演练，季度验证 |
| 超时用框架默认值 | 依赖默认无超时 | 资源泄漏导致雪崩 | 每层显式配置且逐层收敛 |
| 追求 5 个 9 | 盲目对标大厂 | 成本爆炸，收益微小 | 按业务损失反推目标 |
| 复盘写"加强意识" | 无具体动作 | 同类故障复发 | 只接受可验证的动作项 |
