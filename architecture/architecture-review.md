# 架构评审与 ATAM

## 概述

大部分团队的"架构评审"实际是**方案汇报会**：提案人讲 40 分钟架构图，与会者问几个实现细节，
主持人问"大家还有意见吗"，无人反对，签字通过。半年后系统出问题，复盘时发现当初没人评估过可用性。

真正的架构评审只做一件事：**在写代码之前，把这份设计在哪些质量属性上会崩盘找出来**。
ATAM（Architecture Tradeoff Analysis Method，架构权衡分析法）是卡内基梅隆大学 SEI 提出的方法，
它的核心不是流程，而是两件工具：

- **质量属性效用树**——把"系统要快、要稳"变成带数字的场景；
- **六要素场景**——让每个场景都可被验证，而不是可被讨论。

> **架构师判断**：评审会上最该问的一句话不是"这个方案行不行"，而是
> **"这个方案在什么情况下会失效？"** 答不出来的方案还没到评审阶段。

## 前置知识

- 质量属性的含义（性能/可用性/可修改性/安全性/可测试性），见 [[11-软件架构设计|软件架构设计]]
- 架构风格与权衡的基本认知，见 [[architecture-decision-records|架构决策记录（ADR）]]
- 评审通过后的决策需要落档，见 [[architecture/decisions/index|ADR 存档]]

## 什么时候该评审

评审不是每个需求都要过。按**变更的影响面**触发：

| 触发条件 | 示例 | 评审强度 |
|----------|------|----------|
| 引入新的基础设施组件 | 加消息队列、加缓存层、换注册中心 | 完整 ATAM |
| 拆分或合并服务边界 | 订单服务剥离（见 [[architecture/decisions/adr-002-order-service-split|ADR-002]]） | 完整 ATAM |
| 改动跨团队的外部契约 | 对外 API 大版本升级、协议切换 | 轻量评审 |
| 触及数据模型的核心实体 | 订单/账户表结构调整 | 轻量评审 |
| 单模块内部重构 | 内部类结构调整、算法优化 | 不需要（走 code review） |

> 判据和写 ADR 的判据一致：**单向门 + 跨边界**才值得开评审会。

## 第一件工具：六要素场景

"系统要高可用"是无法验收的。"机房断电时，订单服务在 30 秒内切换，不丢已接收的订单" 才可以。
把模糊表述变成可验收场景，需要六个要素：

| 要素 | 含义 | 示例 |
|------|------|------|
| **刺激源** | 谁/什么触发了这件事 | 支付网关 |
| **刺激** | 发生了什么 | 回调请求超时 |
| **制品** | 受影响的部分 | 订单服务 |
| **环境** | 当时系统处于什么状态 | 大促峰值、正常运行 |
| **响应** | 系统做了什么 | 转异步队列受理，前端返回"处理中" |
| **响应度量** | 用哪个数字判断合格 | 30 秒内入队，丢单率 0 |

**缺了响应度量，这个场景就只是愿望**。评审时专门盯这一项：
凡是说不出数字的场景，一律标记为风险。

### 常见质量属性的度量口径

| 质量属性 | 可量化口径 | 陷阱 |
|----------|-----------|------|
| 性能 | P95 / P99 延迟、吞吐 QPS | 只写平均值会掩盖长尾；均值 100ms 但 P99 3s 同样不可用 |
| 可用性 | 年停机时长、MTTR | 混淆"系统可用"与"业务可用"（服务活着但下单失败） |
| 可靠性 | 数据丢失率、错误率 | 与可用性混用；可靠性是"不出错"，可用性是"不中断" |
| 可修改性 | 变更人天、受影响模块数 | 只统计开发时间，漏掉测试与回归成本 |
| 安全性 | 拦截率、漏洞等级与修复时长 | 只写"符合等保"无法验收 |
| 可测试性 | 覆盖率、单测执行时长 | 覆盖率不等于有效性 |

## 第二件工具：质量属性效用树

效用树把业务目标逐层分解到可测量的场景叶子，并给每个叶子打两个标签：

- **业务重要性**（H/M/L）——不做会损失什么；
- **技术难度**（H/M/L）——实现起来有多难。

**（H, H）的叶子是评审会必须优先攻克的**：既重要又难，通常决定架构成败。
（L, H）应当果断砍掉或降级——投入产出比最差。

```text
效用 (Utility)
├── 性能
│   ├── [H,H] 大促峰值 6 倍流量下，订单列表 P95 ≤ 300ms
│   └── [M,H] 报表导出期间，在线交易 P95 波动 ≤ 10%
├── 可用性
│   ├── [H,H] 支付回调超时时，下单仍可受理，30s 内入队且不丢单
│   └── [H,M] 单机房故障时，订单可继续写入，30s 内切换、RPO=0
├── 可修改性
│   └── [M,H] 新增一种支付方式，2 人日内上线
└── 安全性
    └── [M,M] 越权访问他人订单，100% 拦截并留审计
```

### 场景清单（可落成 CSV 供脚本计算）

| 质量属性 | 场景 | 业务重要性 | 技术难度 | 响应度量 | 归属 |
|----------|------|-----------|---------|----------|------|
| 性能 | 大促峰值 6 倍流量下订单列表接口 P95 | H | H | 300ms | 交易组 |
| 可用性 | 支付回调服务不可用时下单仍可受理 | H | H | 降级后 30s 内入队且不丢单 | 交易组 |
| 可用性 | 单机房故障时订单可继续写入 | H | M | 30s 内切换、RPO=0 | — |
| 可修改性 | 新增一种支付方式并上线 | M | H | 2 人日内完成 | 支付组 |
| 性能 | 报表导出不影响在线交易 | M | H | 导出期间在线 P95 波动 10% 以内 | — |
| 安全性 | 越权访问他人订单 | M | M | 100% 拦截并审计 | 安全组 |
| 可测试性 | 订单状态机能被单测覆盖 | M | L | 分支覆盖率 85% | 交易组 |

注意表中两个"—"：**没有归属人的场景等于没人会去做**。这正是评审要暴露的东西。

## ATAM 的六个步骤（实战版）

原版 ATAM 有九个步骤，对多数团队过重。保留下面六步即可获得 80% 的收益：

| 步骤 | 做什么 | 产出 | 常见失手 |
|------|--------|------|----------|
| 1. 业务驱动因子 | 列出业务目标与约束（成本/时间/合规） | 3~5 条驱动因子 | 直接跳进技术方案 |
| 2. 质量属性效用树 | 用六要素场景建树并打 H/M/L | 场景清单（含响应度量） | 场景没有数字 |
| 3. 架构方法陈述 | 提案人讲清方案与**关键取舍** | 架构图 + 已识别的敏感点 | 只讲"做了什么"，不讲"放弃了什么" |
| 4. 场景推演 | 挑 (H,H) 场景逐个走查，追问"这里会怎么坏" | 风险清单 | 走过场，不追问极端情况 |
| 5. 归类输出 | 把发现分为敏感点/权衡点/风险/非风险 | 四类清单（见下节） | 全部记成"待办"，没有分类 |
| 6. 形成结论 | 通过 / 有条件通过 / 打回 | ADR + 风险登记表 | 只写"通过"，风险无人认领 |

### 场景推演怎么追问

对每个 (H,H) 场景，固定追问四个问题（这套问法比任何清单都有效）：

1. **这个场景下，瓶颈最先出现在哪一层？**（数据库连接池？下游接口？线程池？）
2. **如果那一层被打满，故障会横向扩散到哪些功能？**（雪崩路径）
3. **有没有熔断/限流/降级能兜住？阈值是多少，谁配置？**
4. **这个场景你验证过吗？怎么验证的？**（压测数据、故障演练、还是"应该没问题"）

第四个问题最能筛掉纸上方案：**没验证过的性能承诺，一律按风险处理**。

## 输出物：四类发现

ATAM 的价值主要体现在把模糊担忧分类。评审报告必须把发现拆成这四类：

| 类型 | 定义 | 示例 | 处理方式 |
|------|------|------|----------|
| **敏感点**（Sensitivity Point） | 某个决策对某个质量属性影响极大 | 订单库连接池大小直接决定 P95 | 标注，重点压测验证 |
| **权衡点**（Tradeoff Point） | 同时影响多个质量属性，且方向相反 | 加大连接池提升吞吐但增加数据库压力、降低可用性 | 必须记录取舍依据 → 写 ADR |
| **风险**（Risk） | 可能不满足场景的隐患 | 无链路追踪，拆服务后 MTTR 会上升 | 指定责任人与截止时间 |
| **非风险**（Non-Risk） | 看起来危险但实际可控 | 消息队列单点——已有重试与死信补偿 | 记录判断依据，避免后人重复担心 |

> **权衡点是最容易被漏掉的一类**。会上大家热衷于讨论"这个方案有什么风险"，
> 却很少记录"我们为了 A 牺牲了 B"。而后者恰恰是半年后被追问、且无从回答的东西。

### 评审结论的三种形态

| 结论 | 含义 | 后续动作 |
|------|------|----------|
| **通过** | 无阻断性风险 | 决策写入 ADR，风险进登记表 |
| **有条件通过** | 存在风险但可缓解 | 缓解措施 + 责任人 + 截止时间，未完成不得上线 |
| **打回** | (H,H) 场景无可行方案 | 重新设计，不进入排期 |

**禁止"原则通过"**——这是把风险留给未来的委婉说法，等同于没有评审。

## 工具：效用树加权评分

把上面的场景清单存成 CSV，用脚本算出优先级并揪出不可验收的场景：

```csv
质量属性,场景,业务重要性,技术难度,响应度量,归属
性能,大促峰值 6 倍流量下订单列表接口 P95,H,H,300ms,交易组
可用性,支付回调服务不可用时下单仍可受理,H,H,降级后 30s 内入队且不丢单,交易组
可修改性,新增一种支付方式并上线,M,H,2 人日内完成,支付组
安全性,越权访问他人订单,M,M,100% 拦截并审计,安全组
可测试性,订单状态机能被单测覆盖,M,L,分支覆盖率 85%,交易组
性能,报表导出不影响在线交易,M,H,导出期间在线 P95 波动 10% 以内,
可用性,单机房故障时订单可继续写入,H,M,30s 内切换、RPO=0,
```

```python
#!/usr/bin/env python3
"""按 ATAM 效用树规则给质量属性场景排优先级，并揪出不可验证的场景。

用法: python3 rate.py utility-tree.csv
退出码: 0 全部场景可验证; 1 存在缺响应度量或无人负责的场景
"""

import csv
import sys
from collections import Counter

LEVEL = {"H": 3, "M": 2, "L": 1}


def main(path: str) -> int:
    with open(path, newline="", encoding="utf-8") as f:
        rows = list(csv.DictReader(f))

    scored = []
    for r in rows:
        imp = LEVEL.get(r["业务重要性"].strip().upper(), 0)
        dif = LEVEL.get(r["技术难度"].strip().upper(), 0)
        # (H,H) 是评审必须优先攻克的叶子；同档内按重要性再按难度排
        scored.append((imp * dif, imp, dif, r))
    scored.sort(key=lambda t: (-t[0], -t[1], -t[2]))

    for score, _imp, _dif, r in scored:
        mark = "P0" if score >= 9 else "P1" if score >= 4 else "P2"
        print(f"{mark} | {r['质量属性']} | {r['场景']} | "
              f"重要性={r['业务重要性']} 难度={r['技术难度']}")

    print("--- 分布 ---")
    for attr, n in Counter(r["质量属性"] for r in rows).most_common():
        print(f"{attr}: {n}")
    key = sum(1 for s, _, _, _ in scored if s >= 9)
    print(f"(H,H) 关键场景: {key} 个，评审会必须最先谈完")

    problems = 0
    for r in rows:
        if not r["响应度量"].strip():
            print(f"[风险] 「{r['场景']}」没有响应度量，无法验收")
            problems += 1
        if not r["归属"].strip():
            print(f"[风险] 「{r['场景']}」无人负责")
            problems += 1
    return 1 if problems else 0


if __name__ == "__main__":
    raise SystemExit(main(sys.argv[1]))
```

P1 | 可用性 | 单机房故障时订单可继续写入 | 重要性=H 难度=M
P1 | 可修改性 | 新增一种支付方式并上线 | 重要性=M 难度=H

脚本返回非零退出码——**"单机房故障"这种 (H,M) 场景无人认领，是评审必须当场解决的**。

## 一场 90 分钟评审会的议程

| 时长 | 环节 | 谁主导 | 关键要求 |
|------|------|--------|----------|
| 10 min | 业务驱动因子与约束 | 业务方 | 只说约束（预算、时间、合规），不谈技术 |
| 15 min | 效用树与场景确认 | 架构师 | 逐条确认响应度量，当场补不出的标记为风险 |
| 25 min | 提案人陈述方案与取舍 | 提案人 | **必须包含"我们放弃了什么"** |
| 30 min | (H,H) 场景推演 | 全体 | 按上节四个问题逐条追问，记录风险 |
| 5 min | 归类与结论 | 架构师 | 四类发现 + 三种结论之一 |

参与人必须包含：业务方（提供约束）、实现者（会被方案约束的人）、运维/值班（承担故障后果的人）。
**只有架构师和提案人的评审会，等于自我确认。**

材料提前 2 天发：一页架构图 + 效用树场景表 + 已识别的风险。
会上不讲背景、不念文档，直接进入推演。

## 轻量版：小团队不搞 ATAM 怎么办

团队只有 3~5 人、没有专职架构师时，用六个问题代替完整流程，20 分钟能过一遍：

1. 这次改动会让**哪个现有指标**变差？
2. 最坏情况下，故障**扩散到哪几个功能**？边界在哪？
3. 有没有**降级开关**？谁来拨，多久生效？
4. 上线后**用什么数字**判断它工作正常？谁看？
5. 如果**明天要回滚**，需要多久？回滚会丢数据吗？
6. 半年后要改这个决定，**成本有多大**？（→ 决定要不要写 ADR）

六问全部答得出来，就可以开工；第 2、3 问答不出来的，先补设计再排期。

## 常见反模式

| 反模式 | 表现 | 后果 | 纠正 |
|--------|------|------|------|
| 汇报会化 | 提案人讲 40 分钟，无人提问 | 风险未暴露，评审变成背书 | 强制先做场景推演再看图 |
| 场景无度量 | "系统要保证高可用" | 无法验收，上线后各说各话 | 六要素缺一不可，度量必须有数字 |
| 只评功能不评质量 | 讨论接口字段、表结构 | 功能对但性能/可用性崩 | 评审材料必须先交效用树 |
| 风险不认领 | 风险清单只有描述 | 永远不修 | 每条风险必须有责任人和截止时间 |
| 一次评完所有场景 | 60 个场景平均用力 | (H,H) 没谈透 | 只评 (H,H) 与 (H,M)，其余批量处理 |
| 用"原则通过"收场 | 模糊结论 | 风险留给未来 | 三种结论二选一，必须有风险登记 |
