# uv 包管理器

**uv** 是由 Astral（Ruff 的开发者）用 Rust 编写的 Python 包管理器与项目管理器，官方称比 pip 快 10-100 倍。它的定位不是"更快的 pip"，而是**一个二进制文件取代一整套工具链**：

| 被取代的工具 | uv 中的对应命令 |
|---|---|
| `pip` / `pip-tools` | `uv pip install`、`uv pip compile` |
| `virtualenv` / `venv` | `uv venv`（或 `uv sync` 自动创建） |
| `pyenv` | `uv python install` / `uv python pin` |
| `pipx` | `uv tool install` / `uvx` |
| `poetry` / `rye` / `PDM` | `uv init` / `uv add` / `uv lock` / `uv sync` |
| `twine` | `uv publish` |
| `build` | `uv build` |

> 截至 2026 年，uv 仍处于 `0.x` 版本（最新约 0.11.x 系列），CLI 偶有变动。升级前建议扫一眼 [CHANGELOG](https://github.com/astral-sh/uv/blob/main/CHANGELOG.md) 的 breaking 部分，生产 CI 里建议锁定版本。

- 官方文档：<https://docs.astral.sh/uv/>
- 中文翻译文档：<https://uv.doczh.com/>

## 1. 安装

```bash
# macOS / Linux
curl -LsSf https://astral.sh/uv/install.sh | sh

# Windows (PowerShell)
powershell -ExecutionPolicy ByPass -c "irm https://astral.sh/uv/install.ps1 | iex"

# 也可以用 pip / pipx 装，但推荐独立安装以便自更新
pip install uv
pipx install uv
```

通过官方脚本安装后，uv 可以自我更新：

```bash
uv self update
uv self version            # 查看版本
```

> **注意**：用 `pip install uv` 装在系统 Python 里时，`uv self update` 不可用；且会占用你要管理的那个环境。推荐独立安装。

### Shell 补全

```bash
uv generate-shell-completion zsh > ~/.zfunc/_uv    # zsh
uv generate-shell-completion bash > ~/.local/share/bash-completion/completions/uv
```

## 2. 核心概念：一个 uv 项目的构成

执行 `uv init` 后会产生这样一组文件，理解各自职责是掌握 uv 的关键：

```text
myproject/
├── pyproject.toml    # 项目元数据 + 你手写的顶层依赖（人维护）
├── uv.lock           # 精确锁定的全量依赖树，含传递依赖与哈希（工具生成）
├── .python-version   # 项目固定的 Python 版本（可选，但强烈建议提交）
├── .venv/            # 虚拟环境（不提交 Git）
└── hello.py
```

**职责划分是这套工具的灵魂**：`pyproject.toml` 写"我要 requests 和 flask"这类宽泛意图，`uv.lock` 记录"最终定了 requests 2.31.0 + urllib3 2.1.0 + …"的精确结果。**`uv.lock` 必须提交到 Git**，它才是可复现性的来源。

### 命令总览

```bash
uv init myproject            # 初始化项目
uv venv --python 3.12        # 显式创建虚拟环境（通常不需要手动执行）
uv add requests              # 添加依赖（同步写入 pyproject.toml + 更新 lock + 安装）
uv add "flask>=3.0,<4"       # 带约束
uv add --group dev pytest    # 添加到 dev 依赖组（PEP 735 dependency-groups）
uv add --dev pytest          # 等价于 --group dev 的简写
uv remove requests           # 移除依赖
uv sync                      # 按 lock 安装/对齐环境（会移除环境里多余的包）
uv run python script.py      # 在项目环境中运行命令，无需手动 activate
uv run pytest                # 运行已在环境里的可执行文件
uv lock                      # 只更新 lock，不碰环境
uv tree                      # 查看依赖树
uv version                   # 查看/修改项目版本号
uv version --bump minor      # 直接升版本号
uv export --format requirements-txt -o requirements.txt  # 导出成 requirements.txt
uv export --format requirements-txt --no-hashes  # 去掉哈希（部分老工具不认带哈希的格式）
```

> **`uv run` 会自动 sync**：每次运行前先确保环境与 lock 一致。这个"隐式同步"是 uv 好用的主因——你再也不需要先 `source .venv/bin/activate`。

### uv.lock 的工作模式细节

| 场景 | 行为 |
|---|---|
| `uv run` / `uv sync` | 若 `pyproject.toml` 有变，先自动重新 lock 再安装 |
| `uv sync --frozen` | **不检查也不更新** lock，直接用现有 lock（离线/快速场景） |
| `uv sync --locked` | lock 与 `pyproject.toml` 不一致就**报错退出**（**CI 推荐**） |
| `uv lock --check` | 只检查 lock 是否最新，不做修改 |

CI 里用 `--locked`，可以拦住"有人改了 pyproject.toml 但忘了重新 lock"的情况。

## 3. Python 版本管理

uv 内置 Python 版本管理，**不需要 pyenv**。它会区分两类解释器：

- **managed（托管）**：uv 自己下载安装的，来自 Astral 的 [python-build-standalone](https://github.com/astral-sh/python-build-standalone) 预编译发行版（开启 PGO/LTO，比源码编译快得多）
- **system（系统）**：其余所有来源。注意，**即使是你用 pyenv 装的，在 uv 眼里也算 system**

```bash
uv python install 3.12        # 装 3.12 最新补丁版
uv python install 3.12.3      # 装精确版本
uv python install '>=3.8,<3.10'  # 装满足约束的版本
uv python install 3.11 3.12 3.13  # 一次装多个
uv python install pypy        # 也支持 PyPy / GraalPy / Pyodide

uv python list                # 列出已装与可下载的版本
uv python list --all-versions # 含所有补丁版本
uv python list --only-installed
uv python find                # 输出当前会用到的解释器路径
uv python pin 3.12            # 在当前目录写 .python-version
uv python pin --global 3.12   # 写用户级默认版本
uv python uninstall 3.11
```

**版本请求格式**非常灵活，`--python` 支持：

```bash
uv venv --python 3.12          # 版本号（3 / 3.12 / 3.12.3 均可）
uv venv --python '>=3.12,<3.13'  # 版本说明符
uv venv --python 3.13t         # free-threaded（无 GIL）版本
uv venv --python 3.12+freethreaded   # 等价写法
uv venv --python cpython@3.12  # 指定实现
uv venv --python pypy@3.10
uv venv --python /opt/homebrew/bin/python3  # 绝对路径，用某个特定系统解释器
```

**优先级**：命令行 `--python` > `.python-version` 文件 > `pyproject.toml` 的 `requires-python`。uv 向上递归查找 `.python-version`（但不会越过项目/工作区边界），找不到再看用户级配置目录。

若系统里没要求的版本，uv 会**自动下载**（无需先 `uv python install`）。可用 `--managed-python` / `--no-managed-python` 强制只用某一类，或用配置项 `python-preference` 固化偏好。

> `~/.local/bin` 不在 PATH 时，`uv python update-shell` 可帮你加上。`uv python install --default 3.12` 会额外注册无版本号的 `python` / `python3`（实验性）。

## 4. 单文件脚本（PEP 723）

不建项目也能管理依赖——把依赖写进脚本头部，uv 会自动建临时环境：

```bash
uv add --script script.py requests rich
```

```python
# /// script
# requires-python = ">=3.11"
# dependencies = [
#     "requests<3",
#     "rich",
# ]
# ///
import requests
from rich import print

print(requests.get("https://astral.sh").status_code)
```

```bash
uv run script.py              # 自动装依赖到临时环境再执行
uv run --with requests script.py   # 临时附加依赖，不改动文件
uv run --python 3.13 script.py     # 指定解释器版本
uv run --env-file .env script.py   # 加载环境变量文件
```

这个模式特别适合运维脚本、数据处理一次性脚本、CI 片段——**文件自带依赖，拷给谁都能跑**。

## 5. 命令行工具（uvx / uv tool）

装 `ruff`、`black`、`httpie` 这类 Python CLI，不该污染任何项目环境。uv 为每个工具创建隔离环境：

```bash
uvx ruff check .              # uvx = uv tool run 的别名，临时环境运行
uv tool install ruff          # 常驻安装到 ~/.local/bin
uv tool list                  # 查看已装工具
uv tool upgrade ruff          # 升级单个
uv tool upgrade --all         # 全部升级
uv tool uninstall ruff
uvx python@3.12               # 直接起某个版本的 REPL
uvx --from "black[d]" black . # 带 extras 运行
```

> `uvx` 的底层是**缓存 + 临时环境**：同一个工具第二次执行几乎瞬时，但仍不占用你的项目环境。

## 6. uv pip：pip 兼容接口

老项目一时迁移不过来时，可以用 pip 兼容命令无痛提速——语法与 pip 基本一致：

```bash
uv pip install requests              # 装到当前虚拟环境（需先 activate 或有 .venv）
uv pip install -r requirements.txt
uv pip uninstall requests
uv pip list / uv pip show / uv pip freeze
uv pip tree                          # 依赖树（pip 本身没有这个能力）
uv pip check

# 替代 pip-tools
uv pip compile pyproject.toml -o requirements.txt
uv pip compile requirements.in -o requirements.txt
uv pip sync requirements.txt         # 严格对齐：会卸载环境里多余的包
```

代价是：`uv pip` **不维护 lockfile**，也不自动管理虚拟环境，需要你自己先 `uv venv`。它适合做 Docker 里的轻量安装环节（见第 10 节）。

## 7. 构建与发布

```bash
uv build                      # 生成 sdist + wheel 到 dist/
uv build --wheel              # 只构建 wheel
uv publish                    # 上传到 PyPI
uv publish --publish-url https://test.pypi.org/legacy/   # 传到 TestPyPI
```

认证方式（安全性从低到高）：

| 方式 | 用法 |
|---|---|
| API token（命令行） | `uv publish --token pypi-xxx...` |
| API token（环境变量） | `export UV_PUBLISH_TOKEN=pypi-xxx...` |
| **Trusted Publishing（OIDC）** | 在 PyPI 绑定 GitHub 仓库后，workflow 里免密发布，**推荐** |

```bash
uv auth login pypi            # 交互式登录，凭据存入 uv 凭据目录
uv auth token pypi            # 查看令牌
uv auth logout pypi
```

## 8. Workspaces（多包仓库）

Cargo 风格的工作区，适合 monorepo：一个根 `uv.lock` 统一锁定所有成员的版本。

```toml
# 根 pyproject.toml
[tool.uv.workspace]
members = ["packages/*"]
```

```text
repo/
├── pyproject.toml      # 工作区根（含 [tool.uv.workspace]）
├── uv.lock             # 全仓库共享一份锁文件
└── packages/
    ├── core/
    │   └── pyproject.toml
    └── api/
        └── pyproject.toml
```

成员之间可以互相依赖，uv 会自动识别为本地路径依赖：

```toml
# packages/api/pyproject.toml
[project]
dependencies = ["core"]      # 指向工作区内的 core 包

[tool.uv.sources]
core = { workspace = true }  # 显式声明：用工作区成员，不去 PyPI 找
```

```bash
uv workspace list                    # 列出所有成员
uv workspace dir --package core      # 输出某个成员的路径
uv sync --package api                # 只同步某个成员的环境
uv run --all-packages pytest         # 在所有成员中运行
```

## 9. 配置：镜像源与私有源

这是国内用户最需要先配的一步。**注意：`index-url` / `extra-index-url` 已标记为废弃**，新写法是 `[[tool.uv.index]]` 数组表：

```toml
# pyproject.toml
[[tool.uv.index]]
name = "tuna"
url = "https://pypi.tuna.tsinghua.edu.cn/simple"
default = true    # 接管默认索引，等价于禁用 PyPI
```

或独立配置文件 `uv.toml`（顶层键，不需要 `[tool.uv]` 前缀）：

```toml
[[index]]
name = "internal"
url = "https://pkgs.company.com/simple"
default = true

[[index]]
name = "pytorch"
url = "https://download.pytorch.org/whl/cu130"
```

> **`default = true` 的语义要留意**：标记后该索引会被移到优先级列表**末尾**（优先级最低），同时会**停用 PyPI 默认索引**。若只是想追加一个源（如 PyTorch 专用源），不要加 `default = true`。

临时切换或环境变量方式：

```bash
uv sync --index https://pypi.tuna.tsinghua.edu.cn/simple
export UV_DEFAULT_INDEX=https://pypi.tuna.tsinghua.edu.cn/simple
export UV_INDEX=https://pkgs.company.com/simple
```

配置项可能被多处覆盖（项目 `uv.toml` → `pyproject.toml` → 用户级 → 环境变量 → 命令行），排查时加 `--verbose` 可以看到 uv 实际读取了哪些配置文件：

```bash
uv sync --verbose 2>&1 | head -30
```

### 依赖混淆防护：index-strategy

多源场景（公私源并存）下有安全风险：若内网包名被攻击者在公网 PyPI 抢注成更高版本，安装器"挑最新版本"的策略会把恶意包拉进来。uv 用 `--index-strategy` 控制跨源挑选行为：

| 策略 | 行为 |
|---|---|
| `first-index`（**默认**） | 按索引声明顺序，找到第一个匹配就停，**不会**为求更高版本继续翻后面的源 → 天然防混淆 |
| `unsafe-best-match` | 跨所有源挑最高版本（pip 的默认行为） |
| `unsafe-any-match` | 任取一个能找到的版本，不做版本比较；最快但最不严谨 |

```toml
# uv.toml
index-strategy = "first-index"
```

保持默认值即可获得防护；只有在确实需要跨源取最高版本时才显式改为 `unsafe-*` 系列。

### 常用环境变量

| 变量                              | 用途                                                       |
| ------------------------------- | -------------------------------------------------------- |
| `UV_CACHE_DIR`                  | 缓存目录（默认 `~/.cache/uv`，Windows `%LOCALAPPDATA%\uv\cache`） |
| `UV_DEFAULT_INDEX` / `UV_INDEX` | 默认索引 / 额外索引                                              |
| `UV_PYTHON`                     | 指定要用的 Python 版本或路径                                       |
| `UV_PYTHON_INSTALL_DIR`         | 托管 Python 的安装位置                                          |
| `UV_LINK_MODE`                  | 装包时的链接策略（`clone` / `copy` / `hardlink` / `symlink`）      |
| `UV_CONCURRENT_DOWNLOADS`       | 并发下载数，默认 50；网络差时调小                                       |
| `UV_OFFLINE`                    | 完全离线，只用本地缓存                                              |
| `UV_NO_CACHE`                   | 本次操作不读写缓存                                                |
| `UV_PROJECT`                    | 指定项目根目录（配合 `--directory` 场景）                             |
| `UV_PUBLISH_TOKEN`              | 发布用的 PyPI token                                          |

## 10. CI 与 Docker 实践

### Docker 镜像中最省事的写法

```dockerfile
FROM python:3.12-slim
# 从官方镜像复制 uv 二进制，避免额外构建层
COPY --from=ghcr.io/astral-sh/uv:latest /uv /usr/local/bin/uv

WORKDIR /app
# 关键：先只拷依赖文件，充分利用 Docker 层缓存
COPY pyproject.toml uv.lock ./
RUN uv sync --locked --no-install-project --no-dev

COPY . .
RUN uv sync --locked --no-dev
CMD ["uv", "run", "python", "main.py"]
```

几个 flag 的意义：

- `--locked`：lock 与 pyproject 不一致就失败，防止漏 `uv lock`
- `--no-install-project`：不安装项目自身，让其后的代码变更不使依赖层失效
- `--no-dev`：生产镜像排除 dev 依赖组

uv 官方镜像还有 `-bookworm`、`-alpine`、`-distroless` 变体可选。

### GitHub Actions

```yaml
- uses: astral-sh/setup-uv@v5
  with:
    version: "0.11.23"      # 建议锁定版本
    enable-cache: true      # 缓存 ~/.cache/uv
- run: uv sync --locked --all-groups
- run: uv run pytest
```

### 缓存管理

```bash
uv cache dir              # 缓存位置
uv cache clean            # 清理所有未使用的缓存条目
uv cache prune            # 同上（更保守）
uv cache clean ruff       # 只清某个包
```

> uv 用**硬链接**（Windows）或**写时复制**（macOS/Linux）把包从全局缓存挂进虚拟环境，所以同一个包在多个项目间几乎不占额外磁盘，安装也近乎瞬时。若因跨文件系统、rsync 备份等原因需要真实副本，用 `--link-mode copy`。

## 11. 从其他工具迁移

### pip + venv → uv

```bash
# 已有 requirements.txt 的项目，直接就能动
uv venv
uv pip install -r requirements.txt

# 想升级到完整项目管理：
uv init --no-readme          # 在现有目录生成 pyproject.toml
uv add -r requirements.txt   # 从 requirements.txt 批量转为顶层依赖
uv lock
```

### poetry / pip-tools → uv

| 原命令 | uv 对应 |
|---|---|
| `poetry add requests` | `uv add requests` |
| `poetry install` | `uv sync` |
| `poetry lock` | `uv lock` |
| `poetry run pytest` | `uv run pytest` |
| `poetry build` / `poetry publish` | `uv build` / `uv publish` |
| `pip-compile requirements.in` | `uv pip compile requirements.in -o requirements.txt` |
| `pip-sync requirements.txt` | `uv pip sync requirements.txt` |

uv 直接读标准 `pyproject.toml` 的 `[project]` 表，Poetry 的 `[tool.poetry]` 私有段需要做一次转换（`[project]` 迁移后才识别）。

## 12. uv vs 其他工具

| 特性 | uv | pip + venv | Poetry | conda |
|---|---|---|---|---|
| 安装速度 | **10-100x** | 基准 | 慢 | 慢 |
| 锁定文件 | `uv.lock`（通用锁，跨 Python 版本/平台） | 需 pip-tools | `poetry.lock` | `environment.yml`（弱） |
| 虚拟环境管理 | 内置且自动 | 需手动 `venv` + `activate` | 内置 | 内置 |
| Python 版本管理 | 内置（`uv python`） | 需 pyenv | 需 pyenv | 内置 |
| CLI 工具隔离 | `uvx` | 需 pipx | 弱 | 弱 |
| 非 Python 依赖（CUDA/MKL） | ❌ | ❌ | ❌ | ✅ |
| 单文件脚本（PEP 723） | ✅ | ❌ | ❌ | ❌ |
| 构建发布 | 内置 | 需 build + twine | 内置 | 弱 |

> **澄清一点**：常见的说法"pip 依赖解析不准"其实是过时的。pip 自 20.3 起的新解析器是正确的，只是**慢**且错误信息不友好。uv 的真实优势是**快** + **把一整套工具统一成一个** + **显式 lock 保证可复现**，而不是"pip 解错了"。

**选型建议**：

- 新项目、Web/后端/脚本工具 → **uv**
- AI 训练环境，依赖 CUDA/cuDNN/MKL 等非 Python 组件 → **conda / mamba**，conda 环境内仍可用 uv 装纯 Python 包
- 需要发布到 PyPI 的库 → uv 或 Poetry 均可，uv 更快且兼具打包发布能力

## 13. 常见排错

| 现象 | 原因 | 解决 |
|---|---|---|
| `No interpreter found for Python >=3.12` 但本机有 3.12 | uv 优先用托管版本，或系统解释器未被发现 | `uv python install 3.12`；或 `uv python find` 排查；或用 `--python /path/to/python` 明确指定 |
| `The lockfile is not up-to-date with pyproject.toml` | 改了依赖声明但没重新 lock（CI 用 `--locked` 时会报错） | 本地执行 `uv lock` 并提交 `uv.lock` |
| 装包后 `import` 仍然失败 | 没用 `uv run`，直接用了系统 python | 用 `uv run python` 或 `source .venv/bin/activate` |
| 内网私有源 401 | 未配置凭据 | `uv auth login <domain>`，或在 index url 里嵌入凭据；用 `uv sync --verbose` 确认实际生效的 index |
| 下载极慢 / 卡在某个包 | 默认走 PyPI | 配置国内镜像，见第 9 节；或调小 `UV_CONCURRENT_DOWNLOADS` |
| Docker 中 `.venv` 挂载覆盖了 | volume 覆盖了镜像里的虚拟环境 | 改用 `UV_PROJECT_ENVIRONMENT=/opt/venv` 把环境装到非项目目录 |
| `uv: command not found` | 安装脚本写入的 bin 不在 PATH | macOS/Linux 检查 `~/.local/bin`，执行 `uv python update-shell` |
| free-threaded / 无 GIL 版本装不上某些包 | 缺少 `cp313t` wheel | 该包尚未支持 free-threading，退回普通 `3.13` |
