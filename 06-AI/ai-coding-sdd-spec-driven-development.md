# AI 编码中的规范驱动开发（SDD）

> **注意**：本文整理于 2026 年 8 月，内容基于当前 SDD 生态的最新进展。

---

## 一、什么是 SDD？

### 1.1 定义

**规范驱动开发（Spec-Driven Development, SDD）** 是一种将**可执行的规范（Executable Specification）** 置于软件开发生命周期中心的工程方法论。在让 AI 写任何一行代码之前，先用结构化文档描述清楚"要做什么""为什么做""怎么做"。这份"规范"是人类和 AI 都能理解的共识，也是后续所有开发活动的**单一事实来源（Single Source of Truth）**。

与传统需求文档（PRD）的核心区别：

| 维度 | 传统 PRD | SDD 规范 |
|------|----------|----------|
| 主要读者 | 产品和工程人员 | AI Agent + CI 流水线 |
| 歧义解决方式 | 对话、隐性知识 | 显式约束 + 验证规则 |
| 更新频率 | 不频繁，经常过时 | 活文档，随开发进展持续更新 |
| 执行性 | 被动参考文档 | 可执行验证门禁 |

### 1.2 为什么 2025-2026 年爆发

AI 编程经历了四个阶段的进化：

```
阶段 1  Copilot 时代 — AI 补全代码行，开发者掌控全局
阶段 2  Vibe Coding — 扔给 AI 一句话需求，它写一整个功能
阶段 3  质量危机 — 代码能跑但不对，上下文丢失，大项目失控
阶段 4  SDD 兴起 — 用规范约束 AI，在自由和纪律间找平衡
```

Vibe Coding（氛围编程）的核心问题：

- **上下文丢失**：长对话中 AI 遗忘早期设计决策
- **需求漂移**：模糊意图导致 AI 自由发挥，产出偏离预期
- **知识孤岛**：开发过程缺乏可追溯文档，团队协作困难
- **质量不可控**：代码风格不一，缺乏统一的质量标准

行业数据也印证了这一趋势：LLM 生成代码的漏洞率在 9.8%–42.1% 之间（Yan et al., 2025），截至 2026 年 2 月，生产仓库中存活的 AI 引入问题已超过 11 万个。单元测试能验证单个函数，但无法捕捉架构违规、API 契约漂移和跨服务边界的安全反模式——SDD 规范恰恰在系统层面运作，弥补了这一缺口。

### 1.3 一份好的规范包含六个要素

1. **预期结果（Outcomes）**：功能完成后，用户和系统应处于什么状态
2. **范围边界（Scope Boundaries）**：明确什么在范围内、什么不在
3. **约束条件（Constraints）**：技术栈限制、安全基线、性能要求
4. **前置决策（Prior Decisions）**：已有的架构选择和不可回退的决定
5. **任务拆解（Task Breakdown）**：将整体目标分解为可执行的步骤
6. **验证标准（Verification Criteria）**：如何判断功能是否正确完成

## 三、各框架工作流程详解

### 3.1 GitHub Spec Kit

**出品方**：GitHub 官方 | **许可证**：MIT | **安装**：`uv tool install specify-cli`

#### 核心理念

Spec Kit 的哲学是**"宪法先行"（Constitution First）**。引入 `CONSTITUTION.md` 文件，定义项目的最高原则、技术栈限制和安全策略，为所有后续规范提供顶层约束。它将规范视为"活的、可执行的工件"。

#### 工作流程（四阶段验证流）

```
┌─────────────────────────────────────────────────────────────┐
│                    GitHub Spec Kit 工作流                      │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  ① Constitution (宪法)                                      │
│     定义项目不可违背的原则                                     │
│     → CONSTITUTION.md                                       │
│                                                             │
│  ② Specify (规格)                                           │
│     用自然语言描述功能，只说"做什么"不说"怎么做"                │
│     → SPEC.md                                               │
│     · 使用 [NEEDS CLARIFICATION] 标记强制补充缺失细节           │
│                                                             │
│  ③ Plan (方案)                                              │
│     基于规范制定详细实施计划                                   │
│     → PLAN.md                                               │
│     · 数据模型、API 设计、技术选型                              │
│                                                             │
│  ④ Tasks (任务)                                             │
│     拆分为有序、可执行的任务清单                                │
│     → TASKS.md                                              │
│     · 含具体文件路径和验收标准                                  │
│                                                             │
│  ⑤ Implement (实现)                                        │
│     AI 按规格生成代码，自动运行测试                             │
│     · 逐任务执行，每个任务完成后对照规范验证                      │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

#### 核心斜杠命令

| 命令 | 作用 |
|------|------|
| `/speckit.constitution` | 定义项目宪法 |
| `/speckit.specify` | 编写功能规格 |
| `/speckit.plan` | 制定技术方案 |
| `/speckit.tasks` | 生成任务清单 |
| `/speckit.implement` | AI 实现代码 |
| `/speckit.review` | 审查代码是否符合规范 |

#### 适用场景

大型企业项目、对流程规范性要求极高的团队、从零开始构建的复杂系统（Greenfield Projects）。原生支持 GitHub Copilot，兼容 Claude Code、Gemini CLI 等 30+ AI 工具。

### 3.2 OpenSpec

**出品方**：Fission-AI（开源社区） | **许可证**：MIT | **安装**：`npm install -g @fission-ai/openspec`

#### 核心理念

OpenSpec 的定位是**轻量级规范对齐层**——在写代码前让人和 AI 达成共识。它专注于在已有代码库（Brownfield Projects）上进行安全、可控的增量开发。设计特点：

- **零 API 密钥**：完全依赖用户已配置的 AI 工具，无需额外服务
- **增量友好**：通过变更提案机制管理增量修改
- **学习曲线平缓**：命令简洁，几分钟内上手

#### 工作流程（三步法）

```
┌─────────────────────────────────────────────────────────────┐
│                     OpenSpec 工作流                            │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  ① 创建变更 (New)                                           │
│     openspec new <change-name>                              │
│     在 .changes/ 目录生成：                                   │
│     ├── proposal.md   ← 变更提案（业务背景、目标）             │
│     ├── spec.md       ← 规范（输入输出、数据模型、验证规则）    │
│     ├── design.md     ← 设计（技术选型、架构）                 │
│     └── tasks.md      ← 任务（可执行步骤）                    │
│                                                             │
│  ② 实施变更 (Apply)                                         │
│     openspec apply <change-name>                            │
│     AI 助手基于上述规范生成或修改代码                          │
│     · 使用 ADDED/MODIFIED/REMOVED 增量标记                    │
│     · 严格遵循规范确保一致性                                   │
│                                                             │
│  ③ 归档变更 (Archive)                                       │
│     openspec archive <change-name>                          │
│     将规范合并到主 .specs/ 目录，清理临时文件                  │
│     → .specs/ 作为知识库持续积累系统能力基线                    │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

#### 适用场景

中小型团队、个人开发者、需要在存量项目上快速迭代的场景。

### 3.3 AWS Kiro

**出品方**：亚马逊云科技（AWS） | **形态**：Agentic IDE（桌面应用）

#### 核心理念

Kiro 不仅仅是一个 SDD 工具，更是一个端到端的 AI 原生开发平台。它将 SDD 理念深度融入其**双模交互设计**中，是当前最"原生"的规格驱动 AI IDE。

#### 工作流程

```
┌─────────────────────────────────────────────────────────────┐
│                      Kiro 工作流                              │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  三阶段流程（EARS 格式描述）：                                │
│                                                             │
│  ① Requirements (需求)                                     │
│     · 用 EARS 格式描述功能需求                                │
│     · 自动生成用户故事和验收条件                               │
│     · 自动推导边界场景                                       │
│                                                             │
│  ② Design (设计)                                            │
│     · 基于需求生成技术设计文档                                │
│     · 架构图、数据模型、安全考量                              │
│                                                             │
│  ③ Tasks (任务)                                             │
│     · 将设计分解为可执行任务                                  │
│     · 每个任务有明确验收标准                                   │
│                                                             │
│  核心机制：                                                   │
│  · Agent Hooks — 事件驱动自动化                               │
│    （保存文件 → 自动跑测试、刷新文档、安全扫描）                 │
│  · 原子化控制 — 每个 AI 操作可一键回滚                        │
│  · 多专业 Agent 协作（Security Agent, Performance Agent）    │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

#### 适用场景

重度依赖 AWS 生态的企业、需要构建复杂 AI Agent 应用的团队、追求一体化体验和原子化安全性的组织。

### 3.4 BMAD Method

**出品方**：BMAD Code Org（开源） | **许可证**：MIT | **安装**：`npx bmad-method install`

#### 核心理念

BMAD（Build More Architect Dreams）是目前**最完整的企业级 SDD 框架**。它通过 **21+ 个专业化 AI Agent** 模拟一整个具有专业分工的敏捷团队，覆盖从产品发现到产品交付的全生命周期。核心洞察是：不同开发阶段需要不同的专业知识，单一 AI Agent 兼顾所有角色会导致"全面平庸"。

#### 核心角色

| Agent | 人格 | 职责 |
|-------|------|------|
| Analyst (Mary) | 分析师 | 头脑风暴、市场调研、项目简报 |
| PM (John) | 产品经理 | 创建/更新 PRD、Epic 和 Story |
| Architect (Winston) | 架构师 | 系统架构、技术选型、API 设计、DB Schema |
| Developer (Amelia) | 开发者 | Story 实现、快速开发、QA 测试生成 |
| UX Designer (Sally) | UX 设计师 | UX 规范、组件和交互模式 |
| Tech Writer (Paige) | 技术作家 | 文档撰写 |

#### 工作流程（七步法）

```
┌─────────────────────────────────────────────────────────────┐
│                    BMAD Method 工作流                         │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  ① Brainstorm (头脑风暴)                                    │
│     Analyst Agent 收集需求与上下文                            │
│     → 项目简报                                               │
│                                                             │
│  ② Plan (规划)                                              │
│     PM Agent 创建详细 PRD                                    │
│     → PRD 文档                                              │
│                                                             │
│  ③ Architect (架构设计)                                     │
│     Architect Agent 基于 PRD 设计系统架构                     │
│     → 架构决策记录 (ADR)                                     │
│     · 服务边界、数据模型、API 规范、NFR                       │
│                                                             │
│  ④ Develop (开发)                                          │
│     Developer Agent 按 Story 实现，严格不超范围               │
│     · 每个 Story 嵌入 PRD 和 ADR 片段，保留设计意图           │
│     → 实现代码                                               │
│                                                             │
│  ⑤ Review (审查)                                           │
│     验证代码质量、检测错误、确保一致性                         │
│                                                             │
│  ⑥ Test & Secure (测试与安全)                               │
│     运行测试、安全审计、性能优化                              │
│                                                             │
│  ⑦ Deliver (交付)                                          │
│     生成清晰的提交信息，部署上线                               │
│                                                             │
│  文档交接链：                                                │
│  Brief → PRD → ADR → Story → Code → Test → Deliver         │
│  每个 Agent 消费上游文档，产出下游文档                         │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

#### 适用场景

大型企业项目、需要严格合规和角色分工的团队、全生命周期覆盖的复杂系统。已有银行遗留系统迁移（5 万行 COBOL→Java）等企业级验证案例。

### 3.5 GSD (Get Shit Done)

**出品方**：TACHES / glittercowboy（开源） | **许可证**：MIT | **安装**：`npx get-shit-done-cc`

#### 核心理念

GSD 是对 BMAD 和 Spec Kit "过度复杂" 的一种反弹。它拒绝 Sprint 仪式、Story Points 和回顾会议，转而专注于**上下文工程（Context Engineering）**——用独立子代理对抗长会话的质量退化。设计哲学是"复杂性在系统内部，不在你的工作流里"。

#### 工作流程（三阶段漏斗 + 循环）

```
┌─────────────────────────────────────────────────────────────┐
│                       GSD 工作流                              │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  组织结构：Project → Milestone → Phase                       │
│  每个 Phase 遵循固定循环：                                    │
│                                                             │
│  ┌─ Discuss (讨论)──────────────────────────────────────┐   │
│  │  AI 提问提取需求，做 gap 分析（spec 对比代码）          │   │
│  │  /gsd:discuss-phase                                    │   │
│  └──────────────────────────────────────────────────────┘   │
│                          ↓                                  │
│  ┌─ Plan (规划)─────────────────────────────────────────┐   │
│  │  生成带优先级的原子化任务清单（XML 格式）               │   │
│  │  每个计划最多 3 个任务                                  │   │
│  │  /gsd:plan-phase                                       │   │
│  └──────────────────────────────────────────────────────┘   │
│                          ↓                                  │
│  ┌─ Execute (执行)──────────────────────────────────────┐   │
│  │  每个任务在全新子代理中执行（干净 200k tokens）         │   │
│  │  并行 Wave 执行（dependency-aware）                    │   │
│  │  每个任务 = 一次独立 Git 提交                          │   │
│  │  /gsd:execute-phase                                    │   │
│  └──────────────────────────────────────────────────────┘   │
│                          ↓                                  │
│  ┌─ Verify (验证)───────────────────────────────────────┐   │
│  │  四级验证阶梯                                           │   │
│  │  /gsd:verify-work                                      │   │
│  └──────────────────────────────────────────────────────┘   │
│                          ↓                                  │
│           循环回到 Discuss，直到所有 Phase 完成               │
│                                                             │
│  核心机制：                                                  │
│  · 零 Context Rot — 隔离子代理执行                           │
│  · 崩溃恢复 — 可从任意状态恢复                               │
│  · 自动模式 — 全自动执行                                     │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

#### 适用场景

单打独斗的开发者或小团队、需要自主"高级合伙人"的场景、多模块复杂系统。已有案例：一位开发者两周内产出 10 万行代码。

### 3.6 Superpowers

**出品方**：obra（开源） | **许可证**：MIT

#### 核心理念

Superpowers 是一个 Skills 框架，叠加在 Claude Code 等工具之上，强制 AI 采取高级工程师的行为方式，最显著的是**强制 TDD（测试驱动开发）**。它拒绝在创建并通过失败的测试用例之前编写任何实现代码。

#### 工作流程（三阶段硬门禁）

```
┌─────────────────────────────────────────────────────────────┐
│                   Superpowers 工作流                          │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  Phase 1: Design (brainstorming skill)                      │
│  ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━                   │
│  · 探索项目上下文（文件、文档、最近提交）                      │
│  · 逐个提出澄清问题                                          │
│  · 提出 2-3 个方案及权衡                                     │
│  · 逐节呈现设计，获得用户批准                                 │
│  · 写设计文档 → docs/superpowers/specs/                     │
│  · 自检：扫描占位符、矛盾和歧义                              │
│  · 🚫 HARD-GATE: 设计未批准前禁止实现                        │
│                                                             │
│              ↓ (用户审查通过后)                              │
│                                                             │
│  Phase 2: Planning (writing-plans skill)                    │
│  ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━                   │
│  · 文件结构映射（先锁定分解决策）                              │
│  · 标准化头部：目标、架构、技术栈、全局约束                     │
│  · 每个任务 2-5 分钟粒度                                     │
│  · 5 步实现循环：Test → Fail → Implement → Pass → Commit    │
│  · 自检：Spec 覆盖率、占位符扫描、类型一致性                   │
│  → docs/superpowers/plans/                                  │
│                                                             │
│              ↓                                              │
│                                                             │
│  Phase 3: Implementation (subagent-driven-development)      │
│  ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━                   │
│  · 控制器 Agent 为每个任务派遣全新子代理                      │
│  · 在隔离的 git worktree 中工作                              │
│  · 两阶段审查：Spec 合规性 + 代码质量                        │
│  · Critical/Important 级别阻断进度                           │
│  · Minor 级别为建议，不阻断                                  │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

#### 适用场景

希望将"话痨助手"转变为纪律严明的专业工程师的开发者、强调测试和执行证据的团队、快速原型开发。

### 3.7 Ralph Loop

**创造者**：Geoffrey Huntley | **形态**：Claude Code 插件

#### 核心理念

Ralph Loop 提出了一种范式转换：不追求保留一份"完美的上下文"，而是拥抱 **fresh start，让 Git 成为记忆层**。它是一种在自动化循环中运行 AI Agent 的技术，一直迭代直到规范被满足。每一轮迭代都会派生一个新的 Agent 进程，带着干净的上下文窗口启动——从磁盘读取规范、取一项任务、实现它、然后退出。

#### 工作流程

```
┌─────────────────────────────────────────────────────────────┐
│                     Ralph Loop 工作流                        │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  /ralph-loop "实现功能 X"                                    │
│    --max-iterations 20                                      │
│    --completion-promise "DONE"                              │
│                                                             │
│  循环机制：                                                  │
│                                                             │
│  ┌──────────────────────────────────┐                       │
│  │  ① Agent 进程启动（干净上下文）   │                       │
│  │  ② 从磁盘读取规范 + 取一个任务    │                       │
│  │  ③ 实现任务                      │                       │
│  │  ④ 退出                          │                       │
│  └──────────┬───────────────────────┘                       │
│             │                                               │
│             ↓                                               │
│  ┌──────────────────────────────────┐                       │
│  │  ⑤ Stop Hook 拦截退出            │                       │
│  │  ⑥ 重新注入相同提示              │                       │
│  │  ⑦ 检查完成条件                  │                       │
│  └──────────┬───────────────────────┘                       │
│             │                                               │
│             ↓                                               │
│      未完成？→ 回到 ①                                       │
│      已完成？→ 结束                                         │
│                                                             │
│  核心特点：                                                  │
│  · Git 即记忆 — 所有产出提交到 Git，不依赖会话上下文          │
│  · 每轮迭代 = 全新 Agent 进程                               │
│  · 可设置迭代上限和完成条件                                   │
│  · 任务之间干净终止并重启                                    │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

#### 适用场景

反馈体系成熟且具备硬性预算的长任务、CI/CD 流水线中的自主修复（某 DevOps 团队落地后：67% 回归 Bug 自动修复，平均修复时间从 4 小时缩短到 23 分钟）。

### 3.8 Tessl

**出品方**：Tessl AI | **形态**：平台 + CLI + MCP 集成 | **安装**：`npm install -g @tessl/cli`

#### 核心理念

Tessl 代表了 SDD 最激进的方向：**Spec-as-Source（规范即源码）**。在 Tessl 的世界观中，AI 生成的代码应该是可抛弃的。人类工程师唯一需要维护、版本化和审查的是**规范**。代码只是一个中间构建产物——如果你需要修改功能，你编辑 Tessl Spec，然后整个文件重新生成。

#### 工作流程

```
┌─────────────────────────────────────────────────────────────┐
│                      Tessl 工作流                             │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  ① Spec Definition (规范定义)                                │
│     · 用精心制作的规范定义软件项目（vibe-specs）              │
│     · 包含功能需求、API 契约、边界情况和可测试用例            │
│     · 提交到 Git                                             │
│                                                             │
│  ② Context & Guardrails (上下文与护栏)                      │
│     · 定义集成测试                                           │
│     · Tessl 将 vibe-spec 与测试关联，创建不可破坏的护栏       │
│     · 从 Tessl Registry 拉取库的已验证使用规范               │
│       （10000+ 预构建规范，防止 API 幻觉）                   │
│                                                             │
│  ③ Approval Checkpoint (批准检查点)                         │
│     · 用户和利益相关者审查规范                                │
│     · 🚫 关键门禁：在此捕获偏差比修复代码便宜几个数量级        │
│                                                             │
│  ④ Generation Loop (生成循环)                               │
│     · AI Agent 通过 MCP 连接 Tessl 平台                     │
│     · 读取 vibe-spec + 拉取已验证库技能                       │
│     · 持续生成代码直到集成测试通过                           │
│     · 代码 = 一次性产物，规范 = 永久资产                     │
│                                                             │
│  核心机制：                                                  │
│  · Tessl Spec Registry — 10000+ 库使用规范                   │
│  · API 幻觉预防 — 提供数学验证的库使用规范                    │
│  · 自动测试生成 — 规范中的示例行为直接变为回归测试           │
│  · 跨语言移植 — 规范可适配不同环境                           │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

#### 适用场景

前瞻性团队（愿意将 AI 生成代码视为编译产物而非源码）、需要根除 API 幻觉的场景、库维护者（可发布使用规范到 Registry）。

### 3.9 Taskmaster AI

**形态**：MCP Server + CLI | **安装**：通过 MCP 集成到 Cursor/Windsurf

#### 核心理念

Taskmaster AI 解决的是大型项目中的**上下文腐烂（Context Rot）**问题。它充当持久记忆和任务管理层，将 PRD 解析为**有依赖关系的层级任务树**，自动确定执行顺序。

#### 工作流程

```
┌─────────────────────────────────────────────────────────────┐
│                    Taskmaster AI 工作流                      │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  ① PRD 输入                                                 │
│     · 读取产品需求文档                                       │
│     · 支持网络搜索获取新鲜信息                               │
│                                                             │
│  ② 任务分解                                                 │
│     · 将 PRD 解析为有依赖关系的层级任务树                     │
│     · 自动映射新任务如何影响现有代码库                        │
│     · 生成执行顺序（依赖感知）                                │
│                                                             │
│  ③ 持久状态管理                                             │
│     · 记住"全局"架构目标                                     │
│     · 即使 LLM 立即上下文窗口拥挤也能保持                    │
│     · 跨不同会话和工具桥接                                   │
│                                                             │
│  ④ 多模型支持                                               │
│     · 主模型 + 研究模型 + 回退模型                           │
│     · 研究模型层用于拉取新鲜网络信息                         │
│                                                             │
│  核心特点：                                                  │
│  · MCP Server — 可嵌入 Cursor/Windsurf 编辑器                │
│  · 依赖映射 — 自动确定执行顺序                               │
│  · 持久记忆 — 对抗上下文腐烂                                 │
│  · 任务级粒度 — 专注于任务分解而非工作流编排                 │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

#### 适用场景

中大型项目（AI 容易忘记全局上下文的场景）、以 Cursor 为主要 IDE 的团队、需要 PRD 到任务结构化分解的场景。

## 五、组合使用

这些框架并非互斥，而是可以组合使用，形成更强的工程体系。例如构建企业级 AI Coding 体系：

```
企业级组合方案

┌─────────────────────────────────────────────────┐
│                                                 │
│  Tessl     →  描述 API 和工具规范（防幻觉）       │
│  Spec Kit  →  约束生成规则（宪法 + 阶段门禁）     │
│  Kiro      →  对生成结果验收（验证层）            │
│                                                 │
│  类比 DevOps：                                  │
│  Tessl     =  OpenAPI                           │
│  Spec Kit  =  编码规范 + 架构规范                │
│  Kiro      =  单元测试 + 静态扫描               │
│                                                 │
└─────────────────────────────────────────────────┘
```

另一个常见组合是 **bmalph**（BMAD + Ralph Loop），将 BMAD 的规划阶段与 Ralph 的自主执行循环融为一体。

## 六、2026 年趋势展望

1. **范式迁移**：开发者角色从"逐行编码的实施者"转变为"定义目标、审查规范、管理风险的 AI 指挥官"
2. **Agentic IDE 崛起**：IDE 从代码编辑器进化为能理解项目上下文、架构和业务目标的自主循环平台
3. **对话即工程**：软件开发的起点不再是代码，而是结构化的规范对话
4. **合规即代码**：EU AI Act 等法规要求将规范作为合规证据，SDD 天然满足这一需求
5. **Spec-as-Source 趋势**：代码作为生成产物、规范作为唯一永久资产的激进范式正在获得关注
